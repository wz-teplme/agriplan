# AgriPlan 项目文件实现覆盖与未完成清单

核查日期：2026-10-17（Asia/Hong_Kong）。

## 结论

**已经依据两份项目文件生成了可运行的本地 MVP，但没有完整实现两份文件描述的 AgriPlan 系统。当前应定位为“业务流程与可靠执行机制的演示 MVP”，不能称为“完整双 Agent 农业方案系统”。**

上一轮完成的是用户确认的首版范围：本地运行、主方案流程优先、市场演示分支、预留模型配置。完整手册包含的客户市场、专业研制、正式商务交付、报告治理、季末归档、评测与生产运行，大量内容仍在范围之外。

特别需要澄清：即使配置真实模型密钥，现有代码也只让模型选择下一研究动作，方案正文仍由固定模板生成；市场分支也不会因此变成独立市场 Agent。这两项需要继续编写业务与研究代码。

本轮进行了文档对照、源码核查、独立核心能力复核和现有测试复跑，并在一次性临时数据库中验证特定限制。没有修改业务实现，也没有修改正式演示数据库。

## 核查口径

- **已实现**：当前存在实际数据写入、权限/版本控制或可运行处理逻辑；不等于生产验收已完成。
- **部分实现**：有基础流程，但只覆盖文档要求的子集。
- **演示替代**：使用硬编码资料、模板或本地函数验证流程，不能视为对应智能能力或外部系统已经接入。
- **未实现**：没有对应业务接口、数据结构或执行逻辑。
- **未验证**：接口或部分机制存在，但没有对应真实调用、质量评测或故障/负载证据。

以下“技术手册”指根目录《AgriPlan_完整项目开发与技术实现手册_修订版.md》，“业务流程”指根目录另一份按业务流程展开的修订文档。接口名称在原文中多为示例；核查比较行为，不要求源码路径与示例一致。

## 三、本次额外验证的两项限制

在一次性临时数据库运行真实服务函数，未操作正式演示库，得到：

```json
{
  "evidence_count": 0,
  "research_status": "completed",
  "technical_status": "confirmed",
  "unrelated_questions_same_answer": true
}
```

1. **没有证据充分性门槛。** 清空临时知识库后，检索返回空列表，但有 `evidence` 键就被视为完成该动作，随后允许提交模板草稿及技术确认。代码见 `app/research.py:115`、`app/research.py:203`、`app/services.py:227`。这说明目前 technical confirmed 表示人员确认了演示内容，不代表通过了文档描述的专业依据审核。
2. **讨论尚未实现按问题作答。** 对“为什么选择这个方案”和“提前签约锁价怎么办”调用同一任务讨论接口，返回完全相同的固定快照解释。代码见 `app/services.py:261`；`request.message` 被保存，但没有用于构造回答。

这两项是需要后续实现的能力缺口，本轮仅核查并记录，未修改业务代码。

## 五、补齐顺序建议

1. **先补主研制的实际价值**：接入获准专业资料与真实本季输入；让研究产出结构化措施、历史采用/调整理由、可核算多明细草稿；增加主张支持性、硬约束与候选评价门槛。保留人工确认，不能让模型自批。
2. **补对话、补问和局部重研**：按问题解释；明确调整才写草稿；按字段影响重算；恢复重核权限、资料和适用产品/价格；记录模型/提示/规则版本及费用。
3. **把市场能力做成真正第二条研究链**：独立市场状态和工具、当前报价与客户事实、受约束策略及报告；随后接客户登录/资格、共享周报和可选跟踪。是否使用长寿命父子任务按实际等待需求决定。
4. **补正式服务与季末闭环**：AR 交接、报价/客户确认、商务接口、交付任务、局部变更、异常责任、季末双输出与审核案例管理。
5. **最后按运行规模落实生产底座**：数据库/文件迁移、监控费用、限流、故障/负载/升级测试、备份恢复和发布回退。SQLite 是否更换、是否使用 LangGraph/pgvector，应按文档契合度与运行需求决定，不能用换框架代替业务能力实现。

若近期目标只是更可信的面试演示，优先完成第 1、2 项与可复现研究轨迹；不能把尚未完成的两个 Agent、真实 RAG 或上线效果作为现有实现经历。
