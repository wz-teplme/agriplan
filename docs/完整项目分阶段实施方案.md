# AgriPlan 完整项目分阶段实施方案

日期：2026-10-17。依据：两份根目录修订手册与《项目文件实现覆盖与未完成清单》。

## 交付目标

从现有本地流程 MVP 逐步完成：受控主方案研制、独立市场研究、内部与客户业务链、可追溯数据和可验证运行。完成状态按业务能力及验收证据更新，不按页面数、文件数或框架名称计算。

保留现有 FastAPI、工作台、版本、权限与持久作业。在现有项目内按模块增加能力；开发期继续本机运行。真实模型、专业资料、外部集成分别记录接入及验证状态，不能把模拟通过标记为真实联调通过。

## 路线选择

| 路线 | 交付方式 | 主要代价 |
| --- | --- | --- |
| A：现有项目分阶段升级（推荐） | 先补主研制价值及质量门槛，再市场及业务闭环，最后生产运行 | 需要维护增量数据库迁移和阶段兼容 |
| B：一次性重建全技术栈 | 先迁移 PostgreSQL/LangGraph/pgvector 后集中开发 | 现有可运行链路需重新联调，专业能力交付较晚 |
| C：只补主研制 | 完成内部研究，客户市场和整季服务另立项目 | 无法覆盖本次要求的完整项目范围 |

采用路线 A。六阶段顺序推进；每阶段写具体设计/任务、先做失败用例、实现、复核、回归与页面验证。后续设计沿此边界展开，发现原文未确定的真实业务规则时单独列出，不自行补成生产规则。

## 六阶段与验收

| 阶段 | 交付范围 | 完成判据 | 覆盖差距 |
| --- | --- | --- | --- |
| 1：资料、草稿与质量门槛 | 本地资料版本及审核发布/撤回；结构化措施与依据；五维评价及具体问题；技术确认复核；问题相关解释；保留原有页面与数据 | 无依据或失效依据不能确认；不同条件产生不同结构化内容；不同问题读取相关数据；修改后评价不能复用；新增与旧库迁移回归通过 | A01基础、A04基础、A05、A06基础、A10基础、F07基础 |
| 2：主 Agent 完整研究 | 真实模型结构化研制与解释；有限子任务/动作、补查/修复/停止；通用补问；多明细计算；模块级失效与恢复再校验；专业输入、报告及跨季参考 | 有效反馈会改变任务和建议；不编造专业参数；不同缺口可等待恢复；面积/报价/仓储变化只重做相关模块；模型协议、专业评测样本及调用状态可查 | B03—B08、A01—A02、A07—A16、E01/E04部分 |
| 3：独立市场 Agent | 独立目标/事实/状态/问题；报价来源适配；库存、品质、运输、结算、现金目标；可行售粮策略、固定报告及追问版本；内部委派 | 主方案委派与独立研究上下文隔离；未知扣价不补零；无仓储不推荐储粮；回款硬条件决定可行性；新信息保留旧报告并重算 | A03、M03—M05 |
| 4：客户市场入口 | AR/管理员账号及责任关系；名额、邀请、激活、访问资格和到期撤销；客户门户三类分流；共享周报、可选跟踪与提醒 | 不超额、不重放、不串报告；撤销影响新调用和恢复；共享内容无客户私有事实；调度/提醒幂等，旧数据显式标时点 | M01—M02、M06—M07、E01部分 |
| 5：正式业务与整季服务 | AR 接洽与候选确认、交接；报价/客户认可/合同关联；审批付款供应适配；SR→FR交接；阶段任务、实际附件、异常责任、局部变更、季末两类输出 | 技术/商务/执行分别核验；旧批准不能启用新版；暂停只作用于影响范围；计划不充实际；责任有接收与期限；归档输出隔离 | B01—B02、A09、F01—F06、E04部分 |
| 6：生产化与效果验收 | 成本及监控指标、限流、版本清单、生产数据库/文件存储、适用 LangGraph/pgvector 接入、备份恢复、部署回退、故障/压力测试、基线与消融 | 关键运行指标及费用可查；备份恢复与升级中等待任务可复现；真实适配联调有证据；专业质量、工作量和运行成本有测量 | E01—E05、A15—A16完善 |

阶段 1—2 的部分能力会分批落地；“覆盖差距”表示归属，不表示该阶段设计完成时这些差距已经关闭。阶段 6 不把“用了某个库”作为验收；若正式交付需要与手册技术栈一致，则增加对应集成与验证记录。

## 统一架构与数据约束

```text
内部工作台 / 客户市场入口
           ↓
API：身份、角色、对象、用途、版本与参数
           ↓
业务用例：事实 / 资料发布 / 候选评价 / 技术与商务 / 服务任务
           ↓
持久任务 + Worker：领取 / 检查点 / 补问 / 恢复 / 预算
           ↓
主方案 Agent ↔ 独立市场 Agent
           ↓
受控工具：历史 / 专业资料 / 产品与计算 / 市场证据
           ↓
版本化数据库 + 文件存储 + 已获准外部适配器
```

1. API/Worker 延续分离；模型和外部网络调用位于业务事务之外。
2. 角色、客户、地块、种植季、用途和数据范围由服务端确定。等待恢复及结果提交重查当前条件。
3. 事实候选、确认、估计、假设、计算结果分别表示。缺失保持未知；专业参数必须有明确确认和来源。
4. 研究输入 R、候选 C、技术 P、报价、合同、市场报告和执行引用分别版本化，固定内容不原地覆盖。
5. 产品数量与金额由程序计算，生成文本只能引用计算结果，不能另算关键数字。
6. 检索结果必须有出处和适用范围；“相关”与“支持主张”分别检查。模型不能发布资料、改变权限或批准方案。
7. 演示数据、受控测试响应、真实调用及专业验收分别标记。旧演示依据不会因迁移自动成为真实专业依据。
8. SQLite 先采用顺序增量迁移，迁移失败事务回滚；任何破坏性迁移前备份。原件、历史版本及已确认内容不被重置。

## 工具与资料的接入顺序

- 资料先支持人工上传/录入的文本与 Markdown、版本及审核；报告文件、表格和 OCR 在阶段 2 建立原件/提取候选管线。OCR 提取不等于确认。
- 模型复用服务端配置，增加结构化草稿与解释契约；未配置时运行确定性的演示研究，并保持明确标签。不能以固定答案冒充真实模型。
- 市场先支持经确认的人工报价及测试适配器，再接获准实时来源。
- CRM/ERP/OA/财务先定义请求、结果、幂等及 unknown/对账契约，并用受控适配器验证；拿到真实地址、权限和字段后联调。模拟状态不标记为权威批准或付款完成。

## 阶段完成记录

每一阶段必须留下：需求编号 → 实现文件 → 自动检查 → 实际页面操作 → 尚未验证的依赖。原差距清单保留核查时点，实施进度另行更新，不能回写历史检查结果冒充当时已完成。

状态只使用：设计待确认、待实现、实现中、待验收、已验收、依赖外部资料。真实模型质量、农艺效果、外部审批及生产容量必须有对应证据才验收。

## 外部依赖与业务待定项

真实模型密钥在本机 .env 或进程环境配置，不发送到聊天中。专业资料、审核参数及合法行情来源需要用户或专业负责人提供。CRM/ERP/OA 品牌、合同锁价形式、审批付款条件和专业适配阈值按真实资料确定。

缺少这些资料不妨碍本地协议、状态、页面和测试开发，但对应真实接入或专业效果必须保持未验证。自动交易、远程农机控制、任意依赖图和自动学习专业规则不在原文范围。
